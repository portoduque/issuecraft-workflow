# Solution-economy review

## Setup

Before In Review, a diff introduces new abstractions, wrappers, dependencies, configuration, files/modules, or custom implementation.

## Must

- Review new ownership for evidence-backed necessity after correctness/completeness is established.
- Flag duplicated project capability or speculative complexity only when evidence supports the finding.
- Recognize legitimate boundaries, explicit requirements, isolation, compatibility, and risk-control value.
- Record a material known operational ceiling and evidence-based revisit trigger when a deliberate simplification has one.
- Allow a clean solution-economy review to produce zero findings.

## Must not

- Use raw LOC, file count, deletion count, or dependency count as quality scores.
- Manufacture technical debt or TODOs for ordinary simple code.
- Treat every abstraction or dependency as over-engineering.
